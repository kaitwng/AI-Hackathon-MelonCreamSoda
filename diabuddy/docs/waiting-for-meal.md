# Waiting for Meal

The original routine shipped in PR #11. The follow-up in `feat/meal-timer-play-and-rewards` builds on main `832f708`; see [timer experience updates](meal-timer-play-and-rewards.md). This is an optional, family-configured routine, not a recommendation to wait, dose advice, or permission to eat.

## Family controls

Open **Portal → Parent** and unlock the existing parent PIN. Under **Waiting for Meal**, save either a fixed duration chosen by the parent or a minimum/maximum within which the child may choose. No duration is preselected or calculated. The supported UI bounds are 0–60 whole minutes; they are not a recommended waiting period. A child can start the saved fixed duration but cannot change it. Start always previews the duration and revalidates the current policy.

Because Tandem is not connected, explicitly enable **Allow clearly labeled manual and demo routines** to try the feature. Optional family low-glucose guidance and a parent/trusted adult phone number appear in **Parent / help**. A phone number opens the device's dialer; it does not send an alert. Without one, the app explains that help must be contacted directly. Enter only the family's existing guidance, not a plan generated by the app.

The existing parent mechanism is a salted PIN hash with attempt throttling stored in this browser. New saves check that this gate is unlocked, including after a portal switch; a stale form cannot save. It is a prototype access barrier, **not server-side parent/child authorization**, tamper-proof storage, identity verification, or cross-device family sync. Production family controls require server-enforced roles, authenticated family ownership and protected settings storage. No new authentication bypass or device command was introduced. Existing Sites/Dexcom authentication is separate and unchanged.

## Routine behavior

- Nothing starts automatically. Manual routines are explicitly labeled **NOT PUMP VERIFIED**. The mock t:slim widget and its timers are labeled **Demo — simulated pump data**; those events are separate from the real adapter, glucose alerts and reward claims.
- Review the chosen duration, then Start. Play any existing mini-game if desired. A once-per-session invitation offers Choose a mini-game or Maybe later. Either choice keeps the timer running. The shared timer, Stop and Parent / help controls remain outside page content, including in the arcade and parent portal. The banner sticks only while a timer is active and returns to normal scrolling on stop, interruption or completion.
- Saved start/deadline timestamps drive the display, rather than decrementing an in-memory counter. Reload and visibility changes reconcile against the deadline. Another tab's storage changes are reconciled. The app does not run a background monitoring service or guarantee a notification while the browser/app is suspended; overdue completion is shown when it resumes. Device clock changes affect browser wall-clock timers.
- Stop is always available. Neither a timer nor a game gates eating or help. Finishing says **“Your timer has finished.”** and explicitly does not grant medical clearance to eat. No coins are earned for waiting or finishing. Parents may optionally enable a fixed participation reward at the explicit start of a routine following a recent, trusted, confirmed delivered meal bolus. It defaults off, never applies to demo/manual entries, and never scales with dose, carbs, duration or glucose. Event and delivery claim keys are saved with coins and the timer in a single browser-local write. Coins already earned are kept if the routine stops. The unconnected Tandem adapter currently prevents any real event from qualifying. Existing game rewards remain performance-based.
- A changed parent timing policy stops an active routine, rather than changing its duration silently.
- Legacy demo/reward timers are stopped on migration without changing prior coins or deleting customization, journal data or game progress.

## Readings and care priority

Existing G7 reading validation is reused: connected, no connection error, valid G7 mg/dL reading, non-future timestamp, and at most 15 minutes old. Sandbox readings are identified as simulated. Parent low/high boundaries retain the existing **at or below low / at or above high** convention.

A current low-range reading closes an unstarted routine preview, suppresses waiting offers, stops an active routine, pauses an active game, and prioritizes the family's low-glucose plan and parent/help access. This check precedes overdue completion, runs every second, on connection/reading updates, on visibility return and on parent threshold edits. Turning off contextual illustrations does not turn off this care priority. Interrupted timers never auto-resume, even after recovery or reload. Games may be left or resumed explicitly; finishing them is never required.

Missing, disconnected, invalid, future or stale readings select a neutral companion routine and state that current glucose data is unavailable, with the last reading time (or “No reading received”). Old readings never get substituted for a current reading. An unavailable reading cannot establish a low; the app is not an emergency monitor. Existing optional routines may continue with the availability notice. High readings do not extend timers or generate insulin advice.

Low: candy, juice, quiet/sweat illustration. In range: reading, knitting, gentle stretching. High: water, bathroom approach, inspecting a pump screen. The character never administers or recommends a correction. These are fictional illustrations, not claims about the child's symptoms. The existing artwork, activity buttons, manual activities, lesson priority and reduced-motion rendering remain in use. Contextual choices rotate, avoiding a repeat of the previous choice when a new segment begins, including skipped frames and reduced-motion cycles.

## Tandem integration requirement

**There is no live official Tandem adapter in this repository.** `dist/tandem-readonly.js` explicitly reports `available: false` and returns no events. Existing local demo events cannot unlock a device-confirmed routine. This implementation does not scrape the t:slim app, infer boluses from CGM changes, treat carb entries as delivery, or claim that a frontend boolean verifies a medical device event. The real Dexcom OAuth Worker and its credentials are not modified.

Before enabling automatic *offers*, supply a legitimate, authorized, read-only server integration that can verify delivered meal boluses and associate carbs with that same delivery. Its authenticated same-origin response must contain:

```js
{
  id: 'stable-event-identifier',
  deliveryId: 'stable-pump-delivery-identifier',
  source: 'tandem',
  kind: 'meal_bolus',
  status: 'delivered',
  confirmed: true,
  canceled: false,
  carbs: 30,            // actual associated carb entry, not an estimate
  deliveredUnits: 1,    // delivery confirmation only, never used for timing
  deliveredAt: 0,      // epoch milliseconds from validated device record
  receivedAt: 0        // epoch milliseconds from the authenticated server feed
}
```

These are contract examples, not real patient data. `meal-routine-model.js` rejects correction-only, zero/missing carbs, missing/zero delivery, pending, canceled, unconfirmed, malformed, future, or 10-minute-old events. Delivery must not be after server receipt. Stable event **and** pump delivery keys deduplicate repeated notifications and remain consumed across reload once Start is confirmed. Eligibility and policy are checked again at Start, so an offer can expire without starting anything. Bolus records remain in the adapter's transient memory; the routine stores only consumed identifiers, source and timing. The current ledger is browser-local; production replay protection must be enforced by the server per family/device and handle provider ID namespaces. Do not enable this feed on the strength of browser-local fixtures or add unauthenticated ingest endpoints.

If a Tandem service cannot provide those fields and guarantees, retain the manual fallback and unavailable-device explanation. Manual routines are not recorded as verified boluses.
