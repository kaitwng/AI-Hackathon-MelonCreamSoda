# Family account implementation foundation

The current app has no authenticated family accounts or transactional database. The existing Dexcom sandbox session and browser-local parent PIN are not family authentication. `worker/family-domain.mjs` provides provider-independent server-side authorization and a pairing state machine, but is not exposed as an API or wired to storage. It must not be presented as a working account system.

Pairing requires an authenticated parent with `manage_family` on the selected profile, a cryptographically random 256-bit single-use token stored only as a SHA-256 hash, a ten-minute expiry, a child-authenticated request, and an explicit authorized parent confirmation. It rejects already-linked accounts or profiles rather than merging them. A database adapter must implement serializable transactions or row locks and uniqueness constraints for active links and token hashes. An authenticated network layer must apply server-side rate limiting before token lookups, CSRF/origin protection where cookies are used, secure invitation delivery, authorization on every endpoint, and appropriate audit logging without secrets. A pairing token proves possession only; it does not establish guardianship or consent.

Before production, choose an account and database provider, launch jurisdictions and age/consent policy, verified parental-consent method and provider, privacy and security architecture, retention/deletion policy, and payment processor and actual product configuration. A qualified privacy/security and legal review is needed before collecting child or health data. Implement RLS or equivalent server-enforced family isolation, verified webhook handling, replay protection, and transactional entitlement updates before making real accounts, invitations, or paid checkout available.

## Selected providers and configuration still needed

The chosen foundation is Supabase Auth/Postgres and Stripe. `supabase/migrations/202611150001_family_foundation.sql` creates a restrictive initial schema with read-only RLS policies; it has not been applied or exercised against a Supabase instance. No client write policies are enabled. Do not deploy this migration without a security review and integration tests using separate authenticated parent, child, sibling and unrelated-user sessions. `worker/supabase-auth.mjs` validates an access token against Supabase Auth and returns only the verified user ID. It is used by the read-only `GET /api/family/children` endpoint, which queries with the caller’s token and Supabase RLS; the frontend is not connected. The endpoint returns 503 without configuration.

The owner supplied Plus at $5.99/month, Plus at $50/year, and Family at $8.99/month for the United States. Free covers any number of children with basic features; Plus covers one child and Family covers up to five. Paid benefits, taxes, cancellation terms, and a verified parental-consent method remain undecided. `dist/plans.js` holds those display amounts; paid checkout is disabled. Do not configure real payments until the product and policy decisions are finalized.

Provision a Supabase project with Auth, obtain its project URL and publishable key, and configure the service-role key **only as a server secret**, never in frontend code. Provision Stripe in test mode, create the three recurring Prices, configure a Customer Portal, and set its secret key, webhook signing secret, and price IDs as server secrets. Set the application's HTTPS origin in `APP_ORIGIN`. Do not commit credentials or enter them into chat. The corresponding variable names are listed in `.env.example`.

`worker/stripe-client.mjs` contains server-only Checkout and Billing Portal transport helpers; `worker/stripe-signature.mjs` verifies webhook signatures. They are not exposed as routes. A complete integration still needs authenticated, authorized endpoints, persistent customer ownership and duplicate checkout locking, price/configuration validation, a webhook endpoint with raw-body verification, replay-safe transactional event handling, provider-account/livemode checks, current-state reconciliation, entitlement and coverage logic, and end-to-end Stripe test-mode verification. A return from Checkout alone must never grant access.

The read-only endpoint is covered by mocked authentication and query tests, but this does not validate deployed database policies. Writes, onboarding account creation, pairing persistence, consent verification, billing routes, and family UI remain unimplemented.

## Current demo privacy gate

Until an approved consent method and backend enforcement are integrated, onboarding routes both roles to a fictional-data demo without collecting child nickname or age. Browser inputs and local form submissions are available in the prototype. The current app remains a browser-local prototype with legacy state and client code; these controls are not a security boundary. No child-data write API is implemented. Do not deploy for real child or health data until all ingestion paths are reviewed and server-side consent enforcement is implemented and tested. Existing local data is not deleted.
